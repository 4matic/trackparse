`applyEdits(text, edits)` (`apply_edits` in Python and Rust, `ApplyEdits` in Go) takes a
tracklist as text and returns new text. It's built for editors: you get back the lines it changed, and every other line keeps its
bytes and its line ending. The rules are [R13.9](/trackparse/reference/spec/#r139-edits) in the
spec.

In JavaScript an edit is an object with an `op`. In Python it is a plain dict with the same keys,
`"from"` included. In Rust it is a value of the `Edit` enum, made with a function per edit:
`Edit::set_time(line, seconds)`, `Edit::shift_from(seconds, from)`. In Go it is an `Edit` struct,
made with a function per edit as well: `trackparse.SetTime(line, seconds)`,
`trackparse.ShiftFrom(seconds, from)`.

Lines 1 to 4 are untouched, CRLF included. Edits run in order, each on the text the previous one
produced, with line numbers as that text has them.

## The edits

There are six edits. JavaScript and Python write them the same way, as an object or a dict. Rust
and Go have a constructor for each:

| JavaScript and Python | Rust | Go | Effect |
|---|---|---|---|
| `{ op: "set-time", line, seconds }` | `Edit::set_time(line, seconds)` | `SetTime(line, seconds)` | Rewrite the time on that line |
| `{ op: "shift", seconds }` | `Edit::shift(seconds)` | `Shift(seconds)` | Add `seconds` (negative to go back) to every timed line |
| `{ op: "shift", seconds, from }` | `Edit::shift_from(seconds, from)` | `ShiftFrom(seconds, from)` | The same, for every timed line from line `from` on |
| `{ op: "shift", seconds, lines }` | `Edit::shift_lines(seconds, lines)` | `ShiftLines(seconds, lines...)` | The same, for the listed lines only |
| `{ op: "sort-by-time" }` | `Edit::sort_by_time()` | `SortByTime()` | Reorder by time. Untimed lines move with the timed line above them, and lines before the first time stay on top |
| `{ op: "set-rest", line, rest }` | `Edit::set_rest(line, rest)` | `SetRest(line, rest)` | Replace everything after the time, for example with `format(track)` (`format_track`) |
| `{ op: "insert", after, text }` | `Edit::insert(after, text)` | `Insert(after, text)` | Insert a line after line `after` (`0` puts it at the top). It gets the text's usual line ending |
| `{ op: "delete", line }` | `Edit::delete(line)` | `Delete(line)` | Remove a line |

In Python the dict keys are quoted: `{"op": "set-time", "line": 3, "seconds": 90}`. Line numbers
start at 1.

This example sorts a list, rewrites one line's track text with
[`format`](/trackparse/guides/formatting/), inserts a line and deletes one:

<Tabs syncKey="lang">
<TabItem label="JavaScript">

```js
import { format } from "trackparse";

const messy = "04:10 Mefjus ft. Phace - Sleepless\n00:00 Noisia - Stigma\n09:30 Outro";
const rest = format(parseTracklist(messy).entries[0].track, { joiners: "canonical" });
// 'Mefjus feat. Phace - Sleepless'

const tidy = applyEdits(messy, [
  { op: "sort-by-time" },
  { op: "set-rest", line: 2, rest },
  { op: "insert", after: 2, text: "06:45 Phace - Psycho" },
  { op: "delete", line: 4 },
]);

tidy.text;      // '00:00 Noisia - Stigma\n04:10 Mefjus feat. Phace - Sleepless\n06:45 Phace - Psycho'
tidy.changed;   // [ 1, 2, 3 ]
```

## Times keep their style

A rewritten time looks like its neighbours. Hours or no hours, digit widths and fraction digits are
all kept, so `52:47` plus 45 seconds is `53:32`, not `00:53:32`.

When a time without hours crosses the hour, it gains hours in the style the rest of the list uses
(`59:31` → `01:00:16`, or `1:00:16` if the list writes one-digit hours). The edit reports
`style-upgraded` so you know the line got longer.

## Bullets and Markdown stay

A list bullet or Markdown emphasis around a time sits in `lead` and `gap`, so a rewritten time keeps
it. Only the digits change:

```js
const result = applyEdits(text, [{ op: "shift", seconds: 45 }]);

result.text;
// '**[**53:32**] Mefjus - Bandwagon**\n**[**01:00:16**] Alix Perez - Fade Away**'
result.warnings;  // [ { code: 'style-upgraded', edit: 0, line: 2 } ]
```

`set-rest` replaces everything after the gap, including a closing `**` at the end of the line. The
time is still read afterwards, because emphasis next to a time doesn't need a partner. A layered
`w/` line without a time moves with the timed line above it when you sort.

## When an edit can't apply

Edits never throw or panic. A bad one changes nothing and reports why. In Rust the codes are the
enum `EditWarningCode` (`EditInvalid`, `TimeClamped`, `StyleUpgraded`), in Go the string type
`EditWarningCode` (`trackparse.EditWarningCodeEditInvalid` and so on):

| Code | When |
|---|---|
| `edit-invalid` | missing line, no time on the line, `NaN` or infinity, a time too large to write, a line break inside `text` or `rest`, an unknown `op` |
| `time-clamped` | the time would go below zero, so it was set to zero |
| `style-upgraded` | a time gained hours (see above) |

Each edit warning is `{ code, edit, line }`, where `edit` is the index in your `edits` array and
`line` is `null` (`None` in Python and Rust, a `nil` `*int` in Go) when the edit doesn't name a line.
[Warnings](/trackparse/reference/warnings/#edit-warnings) shows how to check them in each language.

## Guarantees

The property tests check these on random text and random edit lists:

- `applyEdits(t, [])` returns `t`.
- An edit never touches a line it doesn't name.
- `shift(+s)` followed by `shift(-s)` gives back the original text, unless something was clamped
  or upgraded on the way.
