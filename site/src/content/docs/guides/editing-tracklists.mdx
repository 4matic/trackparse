[`applyEdits(text, edits)`](/trackparse/reference/tracklist/#applyeditstext-edits-options)
(`apply_edits` in Python and Rust, `ApplyEdits` in Go, `trackparse_apply_edits` in C) takes a
tracklist as text and returns new text. It's built for editors: you get back the lines it changed, and every other line keeps its
bytes and its line ending. The rules are [R13.9](/trackparse/reference/spec/#r139-edits) in the
spec.

In JavaScript an edit is an object with an `op`. In Python it is a plain dict with the same keys,
`"from"` included. In Rust it is a value of the [`Edit`](https://docs.rs/trackparse/latest/trackparse/tracklist/enum.Edit.html) enum, made
with a function per edit: `Edit::set_time(line, seconds)`, `Edit::shift_from(seconds, from)`. In Go
it is an [`Edit`](https://pkg.go.dev/github.com/4matic/trackparse/go#Edit) struct, made with a function per edit as well:
[`trackparse.SetTime(line, seconds)`](https://pkg.go.dev/github.com/4matic/trackparse/go#SetTime), [`trackparse.ShiftFrom(seconds, from)`](https://pkg.go.dev/github.com/4matic/trackparse/go#ShiftFrom).
In C the edits go into a `trackparse_edits` list from `trackparse_edits_new()`, one call per edit
(`trackparse_edits_set_time(edits, line, seconds)`, `trackparse_edits_shift_from(edits, seconds, from)`),
declared in [`trackparse.h`](https://github.com/4matic/trackparse/blob/main/c/include/trackparse.h).
The list copies what it is given, so it can be freed as soon as `trackparse_apply_edits` returns;
the result is freed with `trackparse_edit_result_free`.

Lines 1 to 4 are untouched, CRLF included ([R13.9.1](/trackparse/reference/spec/#r139-edits:~:text=R13.9.1%20Locality)). Edits run in
order, each on the text the previous one produced, with line numbers as that text has them. The
[playground](/trackparse/playground/#list=Hour%202%0A48%3A20%20Noisia%20-%20Stigma%0A52%3A47%20Mefjus%20%26%20Kasra%20-%20Bandwagon%20%28Phace%20Remix%29%0A56%3A05%20Black%20Sun%20Empire%20-%20ID%0A59%3A31%20Alix%20Perez%20-%20Fade%20Away%0A01%3A03%3A10%20Interview%20with%20Hybris%0A01%3A07%3A44%20Imanu%20-%20Sacrifice%0A00%3A11%3A02%20Current%20Value%20feat.%20Teddy%20Killerz%20-%20Payload%0A01%3A15%3A36%20Hybris%20-%20Spinning%20Top)
does the same with buttons: the suggested fix, a shift and a sort, with undo.

## The edits

There are six edits. JavaScript and Python write them the same way, as an object or a dict. Rust
and Go have a constructor for each, and C a function that appends it to a `trackparse_edits` list
(shortened here to the part after `trackparse_edits_`):

| JavaScript and Python | Rust | Go | C | Effect |
|---|---|---|---|---|
| `{ op: "set-time", line, seconds }` | `Edit::set_time(line, seconds)` | `SetTime(line, seconds)` | `set_time(e, line, seconds)` | Rewrite the time on that line |
| `{ op: "shift", seconds }` | `Edit::shift(seconds)` | `Shift(seconds)` | `shift(e, seconds)` | Add `seconds` (negative to go back) to every timed line |
| `{ op: "shift", seconds, from }` | `Edit::shift_from(seconds, from)` | `ShiftFrom(seconds, from)` | `shift_from(e, seconds, from)` | The same, for every timed line from line `from` on |
| `{ op: "shift", seconds, lines }` | `Edit::shift_lines(seconds, lines)` | `ShiftLines(seconds, lines...)` | `shift_lines(e, seconds, lines, count)` | The same, for the listed lines only |
| `{ op: "sort-by-time" }` | `Edit::sort_by_time()` | `SortByTime()` | `sort_by_time(e)` | Reorder by time. Untimed lines move with the timed line above them, and lines before the first time stay on top |
| `{ op: "set-rest", line, rest }` | `Edit::set_rest(line, rest)` | `SetRest(line, rest)` | `set_rest(e, line, rest, len)` | Replace everything after the time, for example with `format(track)` ([`format_track`](/trackparse/reference/functions/#formattrack-options), Go `Format`, C `trackparse_format`) |
| `{ op: "insert", after, text }` | `Edit::insert(after, text)` | `Insert(after, text)` | `insert(e, after, text, len)` | Insert a line after line `after` (`0` puts it at the top). It gets the text's usual line ending |
| `{ op: "delete", line }` | `Edit::delete(line)` | `Delete(line)` | `delete(e, line)` | Remove a line |

In Python the dict keys are quoted: `{"op": "set-time", "line": 3, "seconds": 90}`. Line numbers
start at 1. Sorting is [R13.9.4](/trackparse/reference/spec/#r139-edits:~:text=R13.9.4%20Sort), and inserting and deleting
[R13.9.5](/trackparse/reference/spec/#r139-edits:~:text=R13.9.5%20Insert%20and%20delete).

This example sorts a list, rewrites one line's track text with
[`format`](/trackparse/guides/formatting/), inserts a line and deletes one:

<Tabs syncKey="lang">
<TabItem label="JavaScript">

```js
import { format } from "trackparse";

const messy = "04:10 Mefjus ft. Phace - Sleepless\n00:00 Noisia - Stigma\n09:30 Outro";
const rest = format(parseTracklist(messy).entries[0].track, { joiners: "canonical" });
// 'Mefjus feat. Phace - Sleepless'

const tidy = applyEdits(messy, [
  { op: "sort-by-time" },
  { op: "set-rest", line: 2, rest },
  { op: "insert", after: 2, text: "06:45 Phace - Psycho" },
  { op: "delete", line: 4 },
]);

tidy.text;      // '00:00 Noisia - Stigma\n04:10 Mefjus feat. Phace - Sleepless\n06:45 Phace - Psycho'
tidy.changed;   // [ 1, 2, 3 ]
```

## Times keep their style

A rewritten time looks like its neighbours. Hours or no hours, digit widths and fraction digits are
all kept, so `52:47` plus 45 seconds is `53:32`, not `00:53:32`
([R13.9.2](/trackparse/reference/spec/#r139-edits:~:text=R13.9.2%20Time%20style)).

When a time without hours crosses the hour, it gains hours in the style the rest of the list uses
(`59:31` → `01:00:16`, or `1:00:16` if the list writes one-digit hours). The edit reports
[`style-upgraded`](/trackparse/reference/warnings/#edit-warnings:~:text=style%2Dupgraded) so you know
the line got longer.

## Bullets and Markdown stay

A list bullet or Markdown emphasis around a time sits in `lead` and `gap`
([parts](/trackparse/guides/tracklists/#nothing-is-lost)), so a rewritten time keeps it. Only the
digits change:

`set-rest` replaces everything after the gap, including a closing `**` at the end of the line. The
time is still read afterwards, because emphasis next to a time doesn't need a partner. A layered
`w/` line without a time moves with the timed line above it when you sort.

## When an edit can't apply

Edits never throw or panic. A bad one changes nothing and reports why
([R13.9.6](/trackparse/reference/spec/#r139-edits:~:text=R13.9.6%20Totality)). In Rust the codes are the enum
[`EditWarningCode`](https://docs.rs/trackparse/latest/trackparse/tracklist/enum.EditWarningCode.html) (`EditInvalid`, `TimeClamped`,
`StyleUpgraded`), in Go the string type [`EditWarningCode`](https://pkg.go.dev/github.com/4matic/trackparse/go#EditWarningCode)
(`trackparse.EditWarningCodeEditInvalid` and so on), in C the enum `trackparse_edit_warning_code`
(`TRACKPARSE_EDIT_WARNING_EDIT_INVALID` and so on):

| Code | When |
|---|---|
| `edit-invalid` | missing line, no time on the line, `NaN` or infinity, a time too large to write, a line break inside `text` or `rest`, an unknown `op` |
| `time-clamped` | the time would go below zero, so it was set to zero ([R13.9.3](/trackparse/reference/spec/#r139-edits:~:text=R13.9.3%20Clamp)) |
| `style-upgraded` | a time gained hours (see above) |

Each edit warning is `{ code, edit, line }`, where `edit` is the index in your `edits` array and
`line` is `null` (`None` in Python and Rust, a `nil` `*int` in Go, a `NULL` `const long long *` in C) when the edit doesn't name a line.
[Warnings](/trackparse/reference/warnings/#edit-warnings) shows how to check them in each language.

## Guarantees

The [property tests](/trackparse/project/testing/#properties) check these on random text and
random edit lists:

- `applyEdits(t, [])` returns `t`.
- An edit never touches a line it doesn't name.
- `shift(+s)` followed by `shift(-s)` gives back the original text, unless something was clamped
  or upgraded on the way ([R13.9.7](/trackparse/reference/spec/#r139-edits:~:text=R13.9.7%20Round%20trip)).
