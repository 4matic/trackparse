import { Tabs, TabItem } from "@astrojs/starlight/components";

Mixes and podcasts come with a tracklist: a block of text, one track per line, usually with a start
time in front. `parseTracklist` (`parse_tracklist` in Python and Rust) reads the whole block. Every
line gets its kind, its time and a full [`ParsedTrack`](/trackparse/reference/parse/). The list as a
whole gets checks with line numbers. The rules are [R13](/trackparse/reference/spec/#r13-tracklists)
in the spec, and every field is listed in the [Tracklist API](/trackparse/reference/tracklist/).

<Tabs syncKey="lang">
<TabItem label="JavaScript">

```js
import { parseTracklist } from "trackparse/tracklist";
```

</TabItem>
<TabItem label="Python">

```python
from trackparse.tracklist import parse_tracklist
```

</TabItem>
<TabItem label="Rust">

```rust
use trackparse::tracklist::parse_tracklist;
```

</TabItem>
</Tabs>

In JavaScript it's a separate entry point, `trackparse/tracklist`, about 8.4 KiB gzipped, so code
that only parses single tracks never loads it. In Python it is the module `trackparse.tracklist`,
in Rust the module `trackparse::tracklist`.

Two things differ in Rust. Seconds are `f64`, since a time can carry a fraction, so `Debug` prints
`3167.0` where JavaScript and Python print `3167`. `to_json()` writes `3167`, like the other two.
And `entry.time` and `entry.track` are `Option`s, because a header or a blank line has neither.

## A first list

<Tabs syncKey="lang">
<TabItem label="JavaScript">

```js
const text = [
  "Hour 2",
  "48:20 Noisia - Stigma",
  "52:47 Mefjus & Kasra - Bandwagon (Phace Remix)",
  "56:05 Black Sun Empire - ID",
  "59:31 Alix Perez - Fade Away",
  "01:03:10 Interview with Hybris",
  "01:07:44 Imanu - Sacrifice",
  "00:11:02 Current Value feat. Teddy Killerz - Payload", // typo: should be 01:11:02
  "01:15:36 Hybris - Spinning Top",
].join("\r\n");

const list = parseTracklist(text);

list.entries.map((e) => e.kind);
// [ 'header', 'track', 'track', 'track', 'track', 'marker', 'track', 'track', 'track' ]

const bandwagon = list.entries[2];
bandwagon.time;   // { raw: '52:47', seconds: 3167 }
bandwagon.parts;  // { lead: '', time: '52:47', gap: ' ', rest: 'Mefjus & Kasra - Bandwagon (Phace Remix)' }
bandwagon.track.artists.map((a) => a.name);                                // [ 'Mefjus', 'Kasra' ]
bandwagon.track.versions.map((v) => `${v.type} by ${v.artists[0].name}`);  // [ 'remix by Phace' ]
list.entries[3].track.flags.unknownTitle;                                  // true (the ID)

list.stats;
// { lines: 9, tracks: 7, markers: 1, timed: 8, firstTime: 2900, lastTime: 4536 }
```

## Nothing is lost

Every entry keeps its line exactly as written in `raw`, and its own line ending in `eol`. Joining
`raw + eol` over the entries gives you back the input, byte for byte. CRLF, LF and CR all work, even
mixed in one text, and trailing spaces survive. A last line without a newline has `eol: ""`
([R13.1](/trackparse/reference/spec/#r131-lines-and-the-lossless-guarantee)).

<Tabs syncKey="lang">
<TabItem label="JavaScript">

```js
list.entries.map((e) => e.raw + e.eol).join("") === text;   // true
```

</TabItem>
<TabItem label="Python">

```python
"".join(e.raw + e.eol for e in tl.entries) == text   # True
```

</TabItem>
<TabItem label="Rust">

```rust
list.entries.iter().map(|e| format!("{}{}", e.raw, e.eol)).collect::<String>() == text;   // true
```

</TabItem>
</Tabs>

`parts` cuts `raw` into four strings that join back into it:

| Part | Holds |
|---|---|
| `lead` | spaces, a list bullet (`- `, `* `, `• `), Markdown emphasis or an opening bracket before the time |
| `time` | the time as written, `52:47` |
| `gap` | whatever sits between the time and the track: `] `, ` - `, ` \| `, ` => `, `**] ` |
| `rest` | the track text, which is what gets parsed |

That split is what lets an editor rewrite a time without touching anything else on the line.

## Times

All of these are read as start times:

| Written | Seconds |
|---|---|
| `12:34`, `[12:34]`, `(12:34)` | 754 |
| `1:02:03`, `01:02:03` | 3723 |
| `125:30` (a long mix with no hours) | 7530 |
| `00:00:07.500`, `0:07,5` | 7.5 |

A list bullet in front is fine too, as in lists pasted from Discord or Reddit:
`* 12:34 Artist - Title` and `- [12:34] Artist - Title` are both read at 754 seconds, and the
bullet goes into `lead`.

Something that looks like a time but can't be one, like `1:75` or `0:61:00`, stays in `rest` and
raises an `invalid-time` warning. The time forms are
[R13.2](/trackparse/reference/spec/#r132-times).

## Markdown

Lists copied from Discord, Reddit, Telegram or YouTube comments often keep their Markdown:
`**bold**`, `__underline__`, `*italic*` or `_italic_`, sometimes only around the time. trackparse
reads through it. Emphasis next to the time goes into `lead` and `gap`, so an edit keeps it.
Emphasis in the rest of the line stays in `rest`, but the parser reads the text without it.

<Tabs syncKey="lang">
<TabItem label="JavaScript">

```js
const list = parseTracklist("**[**14:21**] 10. Nitepunk - ID**\n* 18:02 Noisia - _Stigma_");
const [a, b] = list.entries;

a.parts;   // { lead: '**[**', time: '14:21', gap: '**] ', rest: '10. Nitepunk - ID**' }
a.track.artists.map((x) => x.name);   // [ 'Nitepunk' ]
a.track.title;                        // 'ID'
a.track.position;                     // { raw: '10', number: 10 }
b.track.title;                        // 'Stigma'
```

</TabItem>
<TabItem label="Python">

```python
tl = parse_tracklist("**[**14:21**] 10. Nitepunk - ID**\n* 18:02 Noisia - _Stigma_")
a, b = tl.entries

a.parts   # Parts(lead='**[**', time='14:21', gap='**] ', rest='10. Nitepunk - ID**')
[x.name for x in a.track.artists]   # ['Nitepunk']
a.track.title                       # 'ID'
a.track.position                    # Position(raw='10', number=10)
b.track.title                       # 'Stigma'
```

</TabItem>
<TabItem label="Rust">

```rust
let list = parse_tracklist("**[**14:21**] 10. Nitepunk - ID**\n* 18:02 Noisia - _Stigma_");
let (a, b) = (&list.entries[0], &list.entries[1]);

&a.parts;   // Parts { lead: "**[**", time: "14:21", gap: "**] ", rest: "10. Nitepunk - ID**" }
let track = a.track.as_ref().unwrap();
track.artists.iter().map(|x| &x.name).collect::<Vec<_>>();   // ["Nitepunk"]
&track.title;                                                // "ID"
&track.position;                                             // Some(Position { raw: "10", number: 10 })
&b.track.as_ref().unwrap().title;                            // "Stigma"
```

</TabItem>
</Tabs>

Right next to the time, a run of one or two `*` or `_` is read as emphasis by its position, with or
without a partner, so `**14:21 Artist - Title` still has its time. Anywhere else, a `*` or `_` only
counts when it has a partner on the same line and its outer side is a space, a bracket, another `*`
or `_`, or the end of the line. So names keep their stars and underscores: `P*nk`, `*NSYNC`, `DJ_Name`, `Noisia_-_Stigma` and a censored `F**k` come out as
written. Runs of three or more, `~~`, `||` and backticks are never treated as Markdown
([R13.12](/trackparse/reference/spec/#r1312-emphasis-markers)).

## Layered tracks

DJ tracklists mark a track played over the previous one, like an acapella on the second deck, with
`w/` where the track number would go. Such a line gets `layered: true`. The `w/` stays in `rest` and
is left out of the parsed track. An untimed layered line plays at the previous track's time, so it
doesn't warn `time-missing`, and it doesn't count as a neighbour for bare track numbers.

<Tabs syncKey="lang">
<TabItem label="JavaScript">

```js
const list = parseTracklist("00:00 Noisia - Stigma\nw/ Phace - Psycho (Acapella)\n03:10 Mefjus - Sleepless");
const e = list.entries[1];

e.layered;                          // true
e.time;                             // null
e.track.artists.map((a) => a.name); // [ 'Phace' ]
e.track.title;                      // 'Psycho'
list.warnings;                      // []
```

</TabItem>
<TabItem label="Python">

```python
tl = parse_tracklist("00:00 Noisia - Stigma\nw/ Phace - Psycho (Acapella)\n03:10 Mefjus - Sleepless")
e = tl.entries[1]

e.layered                          # True
e.time                             # None
[a.name for a in e.track.artists]  # ['Phace']
e.track.title                      # 'Psycho'
tl.warnings                        # ()
```

</TabItem>
<TabItem label="Rust">

```rust
let list = parse_tracklist("00:00 Noisia - Stigma\nw/ Phace - Psycho (Acapella)\n03:10 Mefjus - Sleepless");
let e = &list.entries[1];

e.layered;                                                   // true
&e.time;                                                     // None
let track = e.track.as_ref().unwrap();
track.artists.iter().map(|a| &a.name).collect::<Vec<_>>();   // ["Phace"]
&track.title;                                                // "Psycho"
&list.warnings;                                              // []
```

</TabItem>
</Tabs>

Only `w/` (or `W/`) at the start of the track text, after any time or bullet, and followed by
whitespace and a track counts, so `00:30 w/ Phace - Psycho` is layered too. `w/` inside a line
(`Noisia w/ Phace - Stigma`), right after a track number (`10. w/ …`) or glued to the name
(`w/Noisia`) is left alone, and so are `with`, `+` and `x`
([R13.13](/trackparse/reference/spec/#r1313-layered-tracks)).

## Line kinds

| Kind | When |
|---|---|
| `track` | a timed line, or an untimed line with an artist/title separator |
| `marker` | no separator and a word like `intro`, `outro`, `break` or `interview` |
| `header` | an untimed line ending in `:`, or something like `Part 2` or `Hour 2` |
| `link` | starts with `http://`, `https://` or `www.` |
| `note` | any other untimed line |
| `blank` | empty or only whitespace |

Only `track` and `marker` entries have a `track`. No line is ever dropped. In Rust the kind is the
enum `EntryKind` (`EntryKind::Track`, `EntryKind::Marker` and so on). The kinds are
[R13.3](/trackparse/reference/spec/#r133-line-kinds).

## Options

`parseTracklist` takes the `parse` options `mode` (default `"tracklist"`), `knownArtists`, `splitAnd`
and `keywords`, plus two of its own. `audioSeconds` is the length of the audio, and turns on the check for times after the end.
`markerWords` adds marker words to the built-in ones:

<Tabs syncKey="lang">
<TabItem label="JavaScript">

```js
const mix = parseTracklist("00:00 Intro\n03:00 Drop\n1:02:03 Noisia - Stigma", {
  audioSeconds: 3600,
  markerWords: ["drop"],
});

mix.entries.map((e) => e.kind);   // [ 'marker', 'marker', 'track' ]
mix.warnings;
// [ { code: 'time-after-audio-end', line: 3, severity: 'warning', suggestion: null } ]
```

</TabItem>
<TabItem label="Python">

```python
mix = parse_tracklist(
    "00:00 Intro\n03:00 Drop\n1:02:03 Noisia - Stigma",
    audio_seconds=3600,
    marker_words=["drop"],
)

[e.kind for e in mix.entries]   # ['marker', 'marker', 'track']
mix.warnings
# (TracklistWarning(code='time-after-audio-end', line=3, severity='warning', suggestion=None),)
```

</TabItem>
<TabItem label="Rust">

```rust
use trackparse::tracklist::{parse_tracklist_with, TracklistOptions};

let options = TracklistOptions::new().audio_seconds(3600.0).marker_words(["drop"]);
let mix = parse_tracklist_with("00:00 Intro\n03:00 Drop\n1:02:03 Noisia - Stigma", &options);

mix.entries.iter().map(|e| e.kind).collect::<Vec<_>>();   // [Marker, Marker, Track]
mix.warnings;
// [TracklistWarning { code: TimeAfterAudioEnd, line: 3, severity: Warning, suggestion: None }]
```

</TabItem>
</Tabs>

Without `markerWords`, `03:00 Drop` is a track line with no separator, and it warns `line-unparsed`.
The options are listed under [Tracklist API](/trackparse/reference/tracklist/#options).

`00:11:02` sits between `01:07:44` and `01:15:36`. Changing one digit gives exactly one time that
fits, `01:11:02`, so the warning carries it as a suggestion. When several fixes would fit, or none
does, `suggestion` is `null` (`None`) and you only get the warning.

Sometimes the typo is on the line before. In `01:22:21` followed by `01:03:55`, the second line is
flagged, but the suggestion is to change the first one to `01:02:21`. All the codes are listed in
[Warnings](/trackparse/reference/warnings/#tracklist-warnings), with an example of handling them in
each language. To apply a suggestion, see
[Editing tracklists](/trackparse/guides/editing-tracklists/).

## Bare track numbers

Some lists number their lines without a dot: `1 Artist - Title`, `2 Artist - Title`. A single
`parse()` call would read `1 Artist` as the artist's name, and it should, because `2 Unlimited`
exists. In a list, trackparse looks at the neighbours: a bare number counts as a position when the
nearest line before or after it carries the next or previous number
([R13.5](/trackparse/reference/spec/#r135-bare-positions)).

## Tracklist mode

Inside a tracklist, the first ` - ` is the separator on almost every line, so each line is
parsed with `mode: "tracklist"` ([Modes](/trackparse/guides/modes/#tracklist-mode)). These lines all go wrong with a plain `parse()` and right in a list:

| Line | `parse(line)` | In a tracklist |
|---|---|---|
| [`Electrosoul System - Liquid Metal`](/trackparse/playground/#track=Electrosoul%20System%20-%20Liquid%20Metal&mode=tracklist) | title `Electrosoul System`, `Liquid Metal` as genre junk | Electrosoul System / `Liquid Metal` |
| [`Effector - 2012`](/trackparse/playground/#track=Effector%20-%202012&mode=tracklist) | title `Effector`, year 2012 | Effector / `2012` |
| [`Paperclip - Anticipation VIP`](/trackparse/playground/#track=Paperclip%20-%20Anticipation%20VIP&mode=tracklist) | title `Paperclip`, a `vip` version | Paperclip / `Anticipation VIP` |
| `8 Linkin Park_-_Points Of Authority (Gydra Bootleg)` | no separator | position 8, Linkin Park / `Points Of Authority`, bootleg by Gydra |
| `10 Optiv & BTK-Inception (Gydra remix)` | no separator | position 10, Optiv, BTK / `Inception`, remix by Gydra |

The first three open in the playground in tracklist mode; set the mode back to `auto` there to see
what a plain `parse()` makes of them. The last two need neighbours: the position needs a 7 or 9 next to it, and the unspaced
`BTK-Inception` dash only splits on a timed line when at least half the list uses spaced dashes.

## JSON

A `Tracklist` serializes like a single track: `JSON.stringify(list)` in JavaScript,
`tl.to_dict()` in Python and `list.to_json()` in Rust give the same JSON, with camelCase keys such
as `specVersion` and `firstTime`. See
[Serializing to JSON](/trackparse/reference/parse/#serializing-to-json).
