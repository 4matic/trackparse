trackparse reads the names of music tracks the way people write them: store metadata, YouTube
titles, file names, scrobbles, the tracklist under a mix. It gives you back an object with the
artists and their roles, the clean title, every remix or version with its credits, and the noise
that was around it.

It comes as four packages with the same behaviour: `trackparse` on
[npm](https://www.npmjs.com/package/trackparse) for JavaScript and TypeScript, `trackparse` on
[PyPI](https://pypi.org/project/trackparse/) for Python, `trackparse` on
[crates.io](https://crates.io/crates/trackparse) for Rust, and the module
[`github.com/4matic/trackparse/go`](https://pkg.go.dev/github.com/4matic/trackparse/go) for Go.
Every example
on this site has a tab for each language. The API docs of the Rust crate are on
[docs.rs](https://docs.rs/trackparse), and those of the Go module on
[pkg.go.dev](https://pkg.go.dev/github.com/4matic/trackparse/go).

Here is what trackparse finds in one line ([try it in the playground](/trackparse/playground/#track=01.%20Wilkinson%20ft.%20Becky%20Hill%20%26%20Tom%20Cane%20-%20Afterglow%20%28Sub%20Focus%20VIP%20Remix%29%20%5BOfficial%20Video%5D)):

```text
01. Wilkinson ft. Becky Hill & Tom Cane - Afterglow (Sub Focus VIP Remix) [Official Video]
└┬┘ └───┬───┘ └───────────┬───────────┘   └───┬───┘ └─────────┬─────────┘ └───────┬──────┘
 │      │                 │                   │               │                   │
 position 1               featured ×2         title           remix · Sub Focus · vip
        │                                                                         │
        primary                                                                   junk: video
```

## The one rule

**Extract, don't delete.** Everything trackparse recognizes goes into a field. Everything it doesn't
recognize stays in the title, verbatim.

Other parsers do less, or more than you want. Some return two strings and leave the rest to you.
Others strip anything in brackets, which turns `(I Can't Get No) Satisfaction` into `Satisfaction`
and loses every remix credit. trackparse would rather leave an odd bracket in the title than throw
away something you needed.

The same rule shows up in smaller ways:

- `[Official Video]` leaves the title, but it lands in [`junk`](/trackparse/guides/junk-and-flags/#junk)
  as `{ raw: "Official Video", kind: "video" }`. An unknown bracket stays in the title as written
  ([R5.8](/trackparse/reference/spec/#r5-group-classification:~:text=R5.8%20Unknown)).
- When the parser had to guess (an unspaced dash, a `"Title" by Artist` pattern), [`warnings`](/trackparse/reference/warnings/) says
  which guess it made. The codes are listed under [Warnings](/trackparse/reference/warnings/).
- Every key of the output is always present, so you never have to check whether a field exists
  ([the output model](/trackparse/reference/spec/#output-model)).
- No string makes it fail. [`parse`](/trackparse/reference/parse/) never throws in JavaScript or
  Python and never panics in Rust or Go
  ([R0.8](/trackparse/reference/spec/#r0-portability:~:text=R0.8%20Parsing%20is)).

All four give this JSON: the packages pass the same fixtures and give the same output on every
fixture input ([Ports](/trackparse/project/ports/#what-the-rust-port-taught) has the one Unicode
note). In JavaScript the result is a plain object. In Python it is a frozen
dataclass with snake_case attributes, and `to_dict()` turns it into the JSON above. In Rust it is a
struct with snake_case fields, and `to_json()` writes that JSON as a string. In Go it is a struct
with exported CamelCase fields, and `json.Marshal` writes that JSON. The
[`parse` reference](/trackparse/reference/parse/) explains every field, and
[Serializing to JSON](/trackparse/reference/parse/#serializing-to-json) shows the round trip in each
language. [Try this track in the playground](/trackparse/playground/#track=Queen%20-%20Bohemian%20Rhapsody%20%28Live%20at%20Wembley%201986%29).

## Names in each language

The docs use the JavaScript and JSON names in running text. Python and Rust use snake_case for the
same things, and Go uses exported CamelCase:

| | JavaScript | Python | Rust | Go |
|---|---|---|---|---|
| Parse | [`parse(s, options?)`](/trackparse/reference/parse/) | `parse(s, **options)` | [`parse(s)`](https://docs.rs/trackparse/latest/trackparse/fn.parse.html), [`parse_with(s, &options)`](https://docs.rs/trackparse/latest/trackparse/fn.parse_with.html) | [`Parse(s)`](https://pkg.go.dev/github.com/4matic/trackparse/go#Parse), [`ParseWith(s, options)`](https://pkg.go.dev/github.com/4matic/trackparse/go#ParseWith) |
| A field | `track.fullTitle` | `track.full_title` | `track.full_title` | `track.FullTitle` |
| An option | [`{ knownArtists: […] }`](/trackparse/reference/options/) | `known_artists=[…]` | [`ParseOptions::new().known_artists([…])`](https://docs.rs/trackparse/latest/trackparse/struct.ParseOptions.html) | [`ParseOptions{KnownArtists: …}`](https://pkg.go.dev/github.com/4matic/trackparse/go#ParseOptions) |
| A value | `"remix"`, `null` | `"remix"`, `None` | `VersionType::Remix`, `None` | `VersionTypeRemix`, `nil` |
| Lists | arrays | tuples | `Vec` | slices |
| JSON | `JSON.stringify(track)` | `track.to_dict()` | `track.to_json()`, or `serde` | `json.Marshal(track)` |

## Spec first

Behaviour isn't defined by the JavaScript code. It's defined by a written
[spec](/trackparse/reference/spec/) with numbered rules (R0 to R13), and by 13,130 fixtures that pin those rules
down. The JavaScript package is the reference implementation. The Python package, the Rust
crate and the Go module pass the same fixtures and produce the same JSON, byte for byte.
[How it's tested](/trackparse/project/testing/) and [Ports](/trackparse/project/ports/) have the
details.

If you wonder why something parses the way it does, there's a rule ID for it, and a fixture that
cites that rule.

## When not to use it

If all you need is a cleaned-up string to send to a scrobbler,
[metadata-filter](https://github.com/web-scrobbler/metadata-filter) is a fine choice and smaller in
scope. trackparse is for when you need to know who did what.

It also has no artist database. `&` is a joiner, so `Chase & Status` comes out as two artists unless
you pass it in [`knownArtists`](/trackparse/reference/options/#parse-options) (`known_artists` in Python and Rust, `KnownArtists` in Go). More on that in
[Artists and credits](/trackparse/guides/artists/#knownartists). The other gaps are listed under
[Limitations and roadmap](/trackparse/project/roadmap/).
