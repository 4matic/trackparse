`parse` never fails on a string. Any string gives a `ParsedTrack`, the empty string included, and
unknown or malformed options fall back to their defaults. What differs between the languages:

- JavaScript ([`trackparse` on npm](https://www.npmjs.com/package/trackparse)): never throws on a string.
- Python ([`trackparse` on PyPI](https://pypi.org/project/trackparse/)): raises `TypeError` if `input` isn't a `str`
  (`parse() expects str input, got int`), and nothing else.
- Rust: takes `&str`, returns the value itself (no `Result`), and never panics. Use
  [`parse`](https://docs.rs/trackparse/latest/trackparse/fn.parse.html) for the defaults and [`parse_with`](https://docs.rs/trackparse/latest/trackparse/fn.parse_with.html) to pass
  options.
- Go: takes a `string`, returns the [`Track`](https://pkg.go.dev/github.com/4matic/trackparse/go#Track) itself (no `error`), and never panics. Use
  [`Parse`](https://pkg.go.dev/github.com/4matic/trackparse/go#Parse) for the defaults and [`ParseWith`](https://pkg.go.dev/github.com/4matic/trackparse/go#ParseWith) to pass options. Bytes that are not valid UTF-8 are read as U+FFFD,
  one per maximal invalid sequence, as Rust's `String::from_utf8_lossy` and the browser's
  `TextDecoder` do.
- C (one header, [`trackparse.h`](https://github.com/4matic/trackparse/blob/main/c/include/trackparse.h)): takes UTF-8 as a pointer and a byte length,
  and returns a `trackparse_track *` that you free with `trackparse_track_free`. Pass
  `TRACKPARSE_NUL_TERMINATED` as the length for a C string; with an explicit length, U+0000 is
  read as a character like any other. Invalid UTF-8 is read as U+FFFD with the same rule as Go
  and Rust. `trackparse_parse_with` takes an options handle, and `NULL` there means the
  defaults. The only failure is running out of memory, reported as `NULL`; no input makes it
  crash.

The options are on the [Options](/trackparse/reference/options/) page. The other functions
([`parseArtists`](/trackparse/reference/functions/#parseartistsinput-options), [`format`](/trackparse/reference/functions/#formattrack-options), [`createParser`](/trackparse/reference/functions/#createparseroptions)) are under
[Other functions](/trackparse/reference/functions/), and the output model is
[defined in the spec](/trackparse/reference/spec/#output-model). To see the whole result for any
input, paste it into the [playground](/trackparse/playground/#track=Noisia%20-%20Stigma%20%282015%29)
and open its JSON view.

The table below uses the JavaScript and JSON names. Python has the same fields as attributes of a
frozen dataclass, in snake_case (`full_title`, `flags.unknown_artist`), with tuples instead of
arrays and `None` instead of `null`. Rust has a struct
([`ParsedTrack`](https://docs.rs/trackparse/latest/trackparse/struct.ParsedTrack.html)) with the same snake_case names as public
fields: `Vec<T>` for arrays, `Option<T>` where the table says `null`, and enums for `mode`, roles,
kinds and warnings. Go has a [`Track`](https://pkg.go.dev/github.com/4matic/trackparse/go#Track) struct with exported CamelCase fields (`FullTitle`,
`Flags.UnknownArtist`): slices for arrays, pointers where the table says `null`, and typed strings
for `mode`, roles, kinds and warnings. C has a read-only `trackparse_track` struct with the same
snake_case names as members: a pointer and a `_count` member for arrays (`versions`,
`versions_count`), pointers that are `NULL` where the table says `null`, C enums for `mode`,
roles, kinds and warnings, and `trackparse_str` for strings (a `ptr` and a `len`; `ptr` is also
NUL-terminated, so `printf("%s")` works on text without U+0000). The track owns everything it
points to, so nothing in it outlives `trackparse_track_free`.

| Field | Type | Description |
|---|---|---|
| `input` | `string` | The original string, untouched (not normalized) |
| `mode` | `"clean" \| "youtube" \| "filename" \| "tracklist"` | The mode that ran ([R2](/trackparse/reference/spec/#r2-mode-prelude)) |
| `position` | `{ raw: string, number: number } \| null` | Track number. `raw` is the digits as written (`"01"`) ([R4](/trackparse/reference/spec/#r4-prefixes-timestamp-and-position)) |
| [`timestamp`](/trackparse/guides/junk-and-flags/#cue-times) | `{ raw: string, seconds: number } \| null` | Leading cue time, `"1:02:03"` → 3723 ([R4](/trackparse/reference/spec/#r4-prefixes-timestamp-and-position)) |
| `artists` | `Artist[]` | Primary, featured and producer credits. Remixers are in `versions` |
| `title` | `string` | The clean title. Brackets it doesn't recognize stay in ([R8](/trackparse/reference/spec/#r8-title-side)) |
| `fullTitle` | `string` | `title` with the versions put back in their original brackets ([R9.4](/trackparse/reference/spec/#r9-assembly-and-dedup:~:text=R9.4%20fullTitle)) |
| `versions` | `Version[]` | Remixes and versions, left to right |
| `year` | `number \| null` | From `(2015)` or `- 2015`, the first in text order ([R9.6](/trackparse/reference/spec/#r9-assembly-and-dedup:~:text=R9.6%20Track%20year)) |
| [`flags`](/trackparse/guides/junk-and-flags/#flags) | `{ explicit, clean, unknownArtist, unknownTitle }` | All booleans ([R5.4](/trackparse/reference/spec/#r5-group-classification:~:text=R5.4%20Flag), [R8.6](/trackparse/reference/spec/#r8-title-side:~:text=R8.6%20Unknown%20title)) |
| [`junk`](/trackparse/guides/junk-and-flags/#junk) | `{ raw: string, kind: JunkKind }[]` | What was taken out of the title, and what kind of noise it was ([R5.1](/trackparse/reference/spec/#r5-group-classification:~:text=R5.1%20Junk)) |
| [`warnings`](/trackparse/reference/warnings/) | `Warning[]` | Which heuristics fired. See [Warnings](/trackparse/reference/warnings/) |

The guides show each field at work: [Modes](/trackparse/guides/modes/) for `mode`,
[Junk, flags and prefixes](/trackparse/guides/junk-and-flags/) for `position`, `timestamp`, `year`,
`flags` and `junk`, [Artists and credits](/trackparse/guides/artists/) for `artists`, and
[Versions and remixes](/trackparse/guides/versions/) for `versions`.

| Field | Values |
|---|---|
| `role` | `primary`, `featured`, `remixer`, `producer` |
| `joiner` | the text before the name as written (`"&"`, `","`, `"ft."`, `"prod. by"`), or `null` for the first name in a list |
| `source` | `artist` (left of the dash), `title` (right of it), `version` (inside a version) |

`&`, `x` and `vs.` are joiners, not roles. Everyone they join is `primary`. In Rust, `role` and
`source` are [`ArtistRole`](https://docs.rs/trackparse/latest/trackparse/enum.ArtistRole.html)`::Primary`,
[`ArtistSource`](https://docs.rs/trackparse/latest/trackparse/enum.ArtistSource.html)`::Artist` and so on; in Go they are
[`trackparse.RolePrimary`](https://pkg.go.dev/github.com/4matic/trackparse/go#RolePrimary), [`trackparse.SourceArtist`](https://pkg.go.dev/github.com/4matic/trackparse/go#SourceArtist) and so
on; in C they are `TRACKPARSE_ROLE_PRIMARY`, `TRACKPARSE_SOURCE_ARTIST` and so on, and
`trackparse_role_name()` and `trackparse_source_name()` give the spec's strings. The splitting rules are [R7](/trackparse/reference/spec/#r7-artist-side).
[Artists and credits](/trackparse/guides/artists/) has examples.

| Field | |
|---|---|
| `type` | one of `remix` `bootleg` `vip` `edit` `flip` `refix` `rework` `mashup` `blend` `dub` `mix` `extended` `radio` `club` `original` `instrumental` `acapella` `live` `acoustic` `remaster` `demo` `reprise` `cover` `version` `spedUp` `slowed` `nightcore` |
| `raw` | the text inside the brackets, as written |
| `artists` | remixers (role `remixer`, source `version`) |
| `modifiers` | type words that didn't become the type: `Extended VIP Mix` → `vip`, `["extended"]` |
| `descriptor` | leftover words: `"Taylor's"`, `"at Wembley"`, `"D'n'B"` |
| `year` | a year inside the version: `Remastered 2015` → 2015 |
| [`unknownArtist`](/trackparse/guides/artists/#unknown-artists) | `true` for `ID Remix` and the like |
| `delimiter` | the bracket it was in, or `-` for a dash suffix |

Python uses `unknown_artist`. Rust uses `unknown_artist` and `version_type`, because `type` is a
reserved word, and `delimiter` is [`VersionDelimiter`](https://docs.rs/trackparse/latest/trackparse/enum.VersionDelimiter.html)`::Paren`,
`Square`, `Curly` or `Dash`. Go uses `Type` (a [`VersionType`](https://pkg.go.dev/github.com/4matic/trackparse/go#VersionType)), `UnknownArtist`
and the [`Delimiter`](https://pkg.go.dev/github.com/4matic/trackparse/go#Delimiter) constants `DelimiterParen`, `DelimiterSquare`,
`DelimiterCurly` and `DelimiterDash`. C uses `type` (a `trackparse_version_type`) and `type_name`
(the spec's string, which differs from `trackparse_version_type_name(type)` only for a type that
[`keywords`](/trackparse/reference/options/#keywords) introduced), `unknown_artist`, and the
delimiters `TRACKPARSE_DELIMITER_PAREN`, `_BRACKET`, `_BRACE` and `_DASH`. The version rules are
[R5.7](/trackparse/reference/spec/#r5-group-classification:~:text=R5.7%20Version).
[Versions and remixes](/trackparse/guides/versions/) explains how the type is chosen.

## Junk kinds

`video`, `audio`, `lyrics`, `quality`, `promo`, `platform`, `label`, `genre`, `other`. Examples are
in [Junk, flags and prefixes](/trackparse/guides/junk-and-flags/#junk). The vocabulary is in
[`spec/data`](https://github.com/4matic/trackparse/tree/main/spec/data). In Rust the kind is the
enum [`JunkKind`](https://docs.rs/trackparse/latest/trackparse/enum.JunkKind.html) (`JunkKind::Video` and so on), in Go the typed string
[`JunkKind`](https://pkg.go.dev/github.com/4matic/trackparse/go#JunkKind) (`trackparse.JunkKindVideo` and so on), in C the enum
`trackparse_junk_kind` (`TRACKPARSE_JUNK_VIDEO` and so on) plus the string `kind_name`.

## Serializing to JSON

All five packages write the same JSON, byte for byte, on every fixture input. The keys are the
camelCase ones of the spec (`fullTitle`, [`unknownArtist`](/trackparse/guides/artists/#unknown-artists)), also in Python, Rust, Go and C.

<Tabs syncKey="lang">
<TabItem label="JavaScript">

```js
import { parse } from "trackparse";

const track = parse("Noisia - Stigma (2015)");

JSON.stringify(track);
// '{"input":"Noisia - Stigma (2015)","mode":"clean","position":null,"timestamp":null,"artists":[{"name":"Noisia","role":"primary","joiner":null,"source":"artist"}],"title":"Stigma","fullTitle":"Stigma","versions":[],"year":2015,"flags":{"explicit":false,"clean":false,"unknownArtist":false,"unknownTitle":false},"junk":[],"warnings":[]}'
```

The result is a plain object, so `JSON.stringify` is all you need, and `JSON.parse` gives the
object back.

</TabItem>
<TabItem label="Python">

```python
import json
from trackparse import ParsedTrack, parse

track = parse("Noisia - Stigma (2015)")

json.dumps(track.to_dict(), separators=(",", ":"), ensure_ascii=False)
# '{"input":"Noisia - Stigma (2015)","mode":"clean","position":null,"timestamp":null,"artists":[{"name":"Noisia","role":"primary","joiner":null,"source":"artist"}],"title":"Stigma","fullTitle":"Stigma","versions":[],"year":2015,"flags":{"explicit":false,"clean":false,"unknownArtist":false,"unknownTitle":false},"junk":[],"warnings":[]}'

ParsedTrack.from_dict(track.to_dict()) == track   # True
```

`ParsedTrack`, `Artist`, `Version`, `Junk`, `Flags`, `Position` and `Timestamp` are frozen
dataclasses. Sequences are tuples, so results are immutable and hashable: you can put them in sets
or use them as dict keys. `to_dict()` gives the spec's JSON shape as a dict, and `from_dict()` goes
the other way. The `separators` and `ensure_ascii` arguments above make `json.dumps` write the
same bytes as JavaScript.

</TabItem>
<TabItem label="Rust">

```rust
use trackparse::{parse, ParsedTrack};

let track = parse("Noisia - Stigma (2015)");

track.to_json();
// "{\"input\":\"Noisia - Stigma (2015)\",\"mode\":\"clean\",\"position\":null,\"timestamp\":null,\"artists\":[{\"name\":\"Noisia\",\"role\":\"primary\",\"joiner\":null,\"source\":\"artist\"}],\"title\":\"Stigma\",\"fullTitle\":\"Stigma\",\"versions\":[],\"year\":2015,\"flags\":{\"explicit\":false,\"clean\":false,\"unknownArtist\":false,\"unknownTitle\":false},\"junk\":[],\"warnings\":[]}"

// with the `serde` feature and serde_json:
let json = serde_json::to_string(&track).unwrap();
json == track.to_json();                                         // true
serde_json::from_str::<ParsedTrack>(&json).unwrap() == track;    // true
```

The results are plain structs that derive `Debug`, `Clone`, `PartialEq` and `Eq`. Each has
[`to_json()`](https://docs.rs/trackparse/latest/trackparse/trait.ToJson.html), which writes the spec's JSON as a compact string and needs no feature and no extra
dependency. With the optional `serde` feature (`cargo add trackparse --features serde`) the result
types, the options and the tracklist `Edit` implement `Serialize` and `Deserialize` with the same
keys, so `serde_json` writes the same text and reads it back.

</TabItem>
<TabItem label="Go">

```go
import (
	"encoding/json"
	"fmt"
	"reflect"

	"github.com/4matic/trackparse/go"
)

track := trackparse.Parse("Noisia - Stigma (2015)")

data, _ := json.Marshal(track)
fmt.Println(string(data))
// {"input":"Noisia - Stigma (2015)","mode":"clean","position":null,"timestamp":null,"artists":[{"name":"Noisia","role":"primary","joiner":null,"source":"artist"}],"title":"Stigma","fullTitle":"Stigma","versions":[],"year":2015,"flags":{"explicit":false,"clean":false,"unknownArtist":false,"unknownTitle":false},"junk":[],"warnings":[]}

var back trackparse.Track
err := json.Unmarshal(data, &back)
fmt.Println(err, reflect.DeepEqual(back, track))   // <nil> true
```

The results are plain structs with exported fields. Every result type has a
[`MarshalJSON`](https://pkg.go.dev/github.com/4matic/trackparse/go#Track.MarshalJSON) method
that writes the spec's JSON, the same bytes as `JSON.stringify` in JavaScript, so
`encoding/json` needs no struct tags or options. `Track` also has
[`UnmarshalJSON`](https://pkg.go.dev/github.com/4matic/trackparse/go#Track.UnmarshalJSON), which reads
that JSON back. Nullable fields are pointers (`*Position`, `*int`), and `json.Marshal` writes them
as `null` when they are `nil`.

</TabItem>
<TabItem label="C">

```c
#include <trackparse.h>

trackparse_track *track = trackparse_parse("Noisia - Stigma (2015)", TRACKPARSE_NUL_TERMINATED);

trackparse_string *json = trackparse_track_to_json(track);
printf("%s\n", json->str.ptr);
// {"input":"Noisia - Stigma (2015)","mode":"clean","position":null,"timestamp":null,"artists":[{"name":"Noisia","role":"primary","joiner":null,"source":"artist"}],"title":"Stigma","fullTitle":"Stigma","versions":[],"year":2015,"flags":{"explicit":false,"clean":false,"unknownArtist":false,"unknownTitle":false},"junk":[],"warnings":[]}
trackparse_string_free(json);
trackparse_track_free(track);
```

`trackparse_track_to_json` returns a `trackparse_string` with the exact bytes `JSON.stringify`
writes in JavaScript. You own it: free it with `trackparse_string_free`. There is one function
per result type: `trackparse_artists_to_json`, `trackparse_tracklist_to_json` and
`trackparse_edit_result_to_json`. The installed library writes JSON but does not read it, so
there is no `from_json`; read the JSON with the JSON library you already use.

</TabItem>
</Tabs>

Tracklist results serialize the same way: `JSON.stringify(list)`, `tl.to_dict()`,
`list.to_json()`, `json.Marshal(list)` and `trackparse_tracklist_to_json(list)`. See the [Tracklist API](/trackparse/reference/tracklist/)
and the [JSON section](/trackparse/guides/tracklists/#json) of the tracklist guide.

  `Mode`. Each has `as_str()` (the spec's name, which `Display` prints too), `from_name()`,
  `FromStr` (its error is `UnknownName`) and `ALL`;
- options: [`ParseOptions`](/trackparse/reference/options/#parse-options), [`KeywordOptions`](/trackparse/reference/options/#keywords), [`FormatOptions`](/trackparse/guides/formatting/#options), with the enums `ModeOption`,
  [`SplitAnd`](/trackparse/guides/artists/#and-is-special), `FeatPlacement`, `JoinerStyle` and `VersionsOption`;
- `Parser`. Every result type has `to_json()`.

```rust
use trackparse::VersionType;

VersionType::SpedUp.as_str();            // "spedUp"
VersionType::from_name("remix");         // Some(Remix)
"bootleg".parse::<VersionType>();        // Ok(Bootleg)
VersionType::ALL.len();                  // 27
```

Most of these enums are `#[non_exhaustive]`, because a later spec version can add a version type or
a warning. A `match` on them needs a `_` arm. The full API is on
[docs.rs](https://docs.rs/trackparse).

</TabItem>
<TabItem label="Go">

All of these are exported from the package (`import "github.com/4matic/trackparse/go"`, package
name `trackparse`):

- structs with exported fields: `Track`, `Artist`, `Version`, `Junk`, `Flags`, `Position`,
  `Timestamp`;
- typed strings: `Role`, `Source`, `VersionType`, `Delimiter`, `JunkKind`, `Warning`, `Mode`. Each
  has a constant per value (`trackparse.RolePrimary`, `trackparse.VersionTypeSpedUp`) and a function
  that returns all values in the spec's order as a new slice (`AllRoles()`, `AllVersionTypes()`). The value is the spec's name,
  so `fmt` prints it as is and a plain conversion reads one;
- options: [`ParseOptions`](/trackparse/reference/options/#parse-options), [`Keywords`](/trackparse/reference/options/#keywords) (with `VersionHead` and `JunkPhrase`), [`FormatOptions`](/trackparse/guides/formatting/#options),
  with the typed strings [`SplitAnd`](/trackparse/guides/artists/#and-is-special), `FeatPlacement`, `JoinerStyle` and `VersionsOption`;
- `Parser`, the type [`NewParser`](/trackparse/reference/functions/#createparseroptions) returns. Every result type has `MarshalJSON`.

```go
fmt.Println(trackparse.VersionTypeSpedUp)              // spedUp
fmt.Println(trackparse.VersionType("remix") == trackparse.VersionTypeRemix)   // true
fmt.Println(len(trackparse.AllVersionTypes()))         // 27
```

A later spec version can add a version type or a warning, so a `switch` on these needs a
`default` case. The full API is on
[pkg.go.dev](https://pkg.go.dev/github.com/4matic/trackparse/go).

</TabItem>
<TabItem label="C">

All of these are declared in `trackparse.h`:

- read-only result structs: `trackparse_track`, `trackparse_artist`, `trackparse_artists` (the
  list `trackparse_parse_artists` returns), `trackparse_version`, `trackparse_junk`,
  `trackparse_flags`, `trackparse_position`, `trackparse_timestamp`, `trackparse_str`, and
  `trackparse_string` (an owned string from `trackparse_format`, `trackparse_normalize` or a
  `_to_json` function);
- enums: `trackparse_role`, `trackparse_source`, `trackparse_version_type`,
  `trackparse_delimiter`, `trackparse_junk_kind`, `trackparse_warning`, `trackparse_mode`. Each
  has a `_name()` function that returns the spec's name, and `trackparse_mode`,
  `trackparse_version_type` and `trackparse_junk_kind` also have `_from_name()`;
- opaque option handles: [`trackparse_parse_options`](/trackparse/reference/options/#parse-options) (which also holds the [keywords](/trackparse/reference/options/#keywords)) and
  [`trackparse_format_options`](/trackparse/guides/formatting/#options), with the enums
  [`trackparse_split_and`](/trackparse/guides/artists/#and-is-special), `trackparse_feat`,
  `trackparse_joiners` and `trackparse_versions`;
- `trackparse_parser`, the handle [`trackparse_parser_new`](/trackparse/reference/functions/#createparseroptions) returns.

```c
printf("%s\n", trackparse_version_type_name(TRACKPARSE_VERSION_SPED_UP));   // spedUp
trackparse_version_type vt;
if (trackparse_version_type_from_name("remix", TRACKPARSE_NUL_TERMINATED, &vt)) {
  printf("%d\n", vt == TRACKPARSE_VERSION_REMIX);   // 1
}
printf("%d\n", TRACKPARSE_VERSION_NIGHTCORE + 1);   // 27
```

The values of each enum are in the spec's order, so the last one plus one is the count. A later
spec version can add a version type or a warning, so a `switch` on these needs a `default` case.

</TabItem>
